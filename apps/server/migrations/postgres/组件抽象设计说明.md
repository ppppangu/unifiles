# 基于组件抽象的数据库设计说明

## 🎯 核心设计理念

系统采用分层设计，以实现数据处理流程的清晰、解耦和可扩展。核心数据流如下：

```
文件上传 (files) → 内容提取 (extracted_documents) → 知识库文档 (documents) → 组件化 (components) → 具体实现 (chunks/photos)
```

## 🏗️ 清晰的抽象层次

### 1. 文件管理层：文件的入口与记录

这是数据处理的起点，负责记录用户上传的每一个原始文件。

-   `files`: 存储上传文件的元数据，如文件名、大小、哈希值、所有者以及处理状态。它是文件生命周期管理的入口。
-   `file_processing_logs`: 记录文件处理各阶段（如上传、验证）的日志，便于追踪和调试。

### 2. 提取层：文档为核心

负责将原始文件转换为标准化的、可处理的内容。

-   `extracted_documents`: 存储从原始文件OCR或转换后的完整Markdown内容。这是内容的“单一真实来源”，确保信息无损。
-   `extracted_assets`: 存储从文档中提取的二进制资源，如图片、表格的可视化表示等，并与 `extracted_documents` 关联, 但核心还是extracted_documents。

### 3. 知识库层：文档的组织

负责将提取的内容组织成逻辑上的文档，并为下一步的组件化做准备。

-   `knowledge_bases`: 用户创建的知识库，作为文档的顶层组织单元。
-   `documents`: 知识库中的一个具体文档实例。它**引用**一个 `extracted_documents`，并可以关联特定的分块策略。这实现了“一次提取，多次使用”。

### 4. 组件层：内容的原子化

这是检索的核心层，负责将文档内容分解为可独立检索的原子单元。

-   `components`: 对分块后的内容进行统一抽象，无论是文本还是图片，都被视为一个“组件”。它包含统一的向量字段 `embedding` 用于检索。
-   `chunks`: 文本组件的子类实现，存储具体的文本内容和相关属性。
-   `photos`: 图片组件的子类实现，存储图片的描述、元数据，并**引用** `extracted_assets` 中的原始资源。

### 组件的统一抽象设计

```sql
-- 组件表：统一抽象
components {
    id,                         -- 主键
    document_id,                -- 关联的知识库文档
    component_type,             -- 组件类型 ('chunk' 或 'photo')
    component_index,            -- 在文档中的顺序
    content,                    -- 组件的文本内容或描述
    embedding                   -- 统一的向量字段
}

-- 文本子类：继承组件
chunks {
    id,                         -- 主键
    component_id (1:1),         -- 关联组件
    text_content,               -- 详细文本内容
    char_count, word_count, token_count -- 文本统计
}

-- 图片子类：继承组件
photos {
    id,                         -- 主键
    component_id (1:1),         -- 关联组件
    extracted_asset_id,         -- 引用原始资源
    photo_description,          -- 图片描述
    alt_text,                   -- 替代文本
    photo_subtype,              -- 图片子类型 (image/chart/diagram)
    width, height, file_size, format -- 图片元数据
}
```

## 🔄 业务流程

### 阶段1：文件上传与提取
1.  **文件上传**: 用户通过API上传文件，在 `files` 表中创建一条记录，包含文件元数据和处理状态（如 `uploaded`）。
2.  **内容提取**: 后台任务触发，调用内容提取引擎（如OCR服务）。
3.  **存储提取结果**: 引擎将文件内容转换为完整Markdown，存入 `extracted_documents` 表。提取出的图片等资源存入 `extracted_assets` 表。

### 阶段2：知识库索引
1.  **创建知识库文档**: 用户将一个已提取的文档（`extracted_documents`）添加到一个知识库（`knowledge_bases`），此时在 `documents` 表中创建一条记录，将两者关联起来。
2.  **应用分块策略**: 系统根据 `documents` 或 `knowledge_bases` 上定义的分块策略，开始处理 `extracted_documents` 中的Markdown内容。
3.  **生成组件**:
    -   文本内容被分割成 `chunks`，并为每个chunk创建一条 `components` 记录和一条 `chunks` 记录。
    -   Markdown中的图片引用被处理成 `photos`，并为每个photo创建一条 `components` 记录和一条 `photos` 记录。`photos` 记录会引用 `extracted_assets` 中的对应资源。
4.  **向量化**: 所有 `components` 的 `content` 字段被向量化，存入 `embedding` 字段。

## 🎯 设计优势

### 1. 清晰的抽象层次
-   **文件层**：负责原始文件的持久化和状态跟踪。
-   **提取层**：负责生成标准化的、无信息丢失的内容源。
-   **知识库层**：负责内容的逻辑组织和策略定义。
-   **组件层**：负责内容的原子化和统一检索。

### 2. 高度的灵活性
同一个 `extracted_documents` 可以被不同的 `documents` 实例引用，每个实例可以应用不同的分块策略，从而生成不同的 `components` 集合，以适应不同的检索场景，而无需重新进行OCR。

```sql
-- 同一个提取文档，用于两个不同的知识库文档，采用不同分块策略
-- 文档A (用于精确问答)
INSERT INTO documents (knowledge_base_id, extracted_document_id, chunking_strategy)
VALUES ('kb_qa', 'extracted_doc_1', '{"strategy": "small_chunks"}');

-- 文档B (用于篇章总结)
INSERT INTO documents (knowledge_base_id, extracted_document_id, chunking_strategy)
VALUES ('kb_summary', 'extracted_doc_1', '{"strategy": "large_chunks"}');
```

### 3. 统一的检索接口
所有检索（无论是文本还是图片）都可以在 `components` 表上进行统一的向量查询，简化了检索逻辑。通过关联 `chunks` 或 `photos` 表可以获取具体内容。

```sql
-- 统一在components层检索
SELECT c.*, 
       CASE 
         WHEN c.component_type = 'chunk' THEN ch.text_content
         WHEN c.component_type = 'photo' THEN p.photo_description
       END as full_content
FROM components c
LEFT JOIN chunks ch ON c.id = ch.component_id AND c.component_type = 'chunk'
LEFT JOIN photos p ON c.id = p.component_id AND c.component_type = 'photo'
WHERE c.embedding <-> $query_vector < 0.5
ORDER BY c.embedding <-> $query_vector;
```

### 4. 零数据冗余
-   原始文件只存一份。
-   提取后的Markdown内容（`extracted_documents`）作为单一真实来源，也只存一份。
-   知识库中的 `documents` 只是对提取内容的引用。
-   `photos` 组件只是对 `extracted_assets` 资源的引用。

## 📝 核心表说明 (根据SQL定义更新)

### files (文件管理)
-   **职责**: 记录用户上传的原始文件信息。
-   **核心字段**: `id`, `user_id`, `filename`, `bytes`, `file_hash`, `storage_path`, `status`。

### extracted_documents (提取文档)
-   **职责**: 存储OCR或转换后的完整Markdown文档。
-   **核心字段**: `id`, `file_id`, `full_markdown`, `structured_content`, `total_pages`, `extraction_status`。

### documents (知识库文档)
-   **职责**: 知识库中的文档实例，是对提取内容的引用。
-   **核心字段**: `id`, `knowledge_base_id`, `extracted_document_id`, `title`, `chunking_strategy`, `processing_status`。

### components (组件抽象)
-   **职责**: 分块后的统一组件抽象，是检索的基本单位。
-   **核心字段**: `id`, `document_id`, `component_type`, `component_index`, `content`, `embedding`。

### chunks (文本组件)
-   **职责**: 文本组件的特化实现。
-   **核心字段**: `id`, `component_id` (1:1), `text_content`, `char_count`, `word_count`, `token_count`。

### photos (图片组件)
-   **职责**: 图片组件的特化实现。
-   **核心字段**: `id`, `component_id` (1:1), `extracted_asset_id` (引用), `photo_description`, `alt_text`, `photo_subtype`。

## 🔍 查询示例

### 1. 混合检索（文本+图片）
```sql
-- 统一在components层进行向量检索，然后关联子表获取详细信息
WITH similar_components AS (
  SELECT id, document_id, component_type, component_index, content, (embedding <-> $query_vector) as distance
  FROM unifiles.components
  WHERE document_id IN (SELECT id FROM unifiles.documents WHERE knowledge_base_id = $kb_id)
  ORDER BY distance
  LIMIT 20
)
SELECT 
  sc.id, sc.component_type, sc.content, sc.distance,
  -- 获取文本块的详细内容
  ch.text_content,
  -- 获取图片块的描述和URL
  p.photo_description,
  ea.storage_path as asset_path
FROM similar_components sc
LEFT JOIN unifiles.chunks ch ON sc.id = ch.component_id AND sc.component_type = 'chunk'
LEFT JOIN unifiles.photos p ON sc.id = p.component_id AND sc.component_type = 'photo'
LEFT JOIN unifiles.extracted_assets ea ON p.extracted_asset_id = ea.id
ORDER BY sc.distance;
```

### 2. 文档重新分块
```sql
-- 1. 删除旧的组件和子类记录
DELETE FROM unifiles.components WHERE document_id = $doc_id;

-- 2. 更新文档的分块策略和状态
UPDATE unifiles.documents
SET 
  chunking_strategy = $new_strategy,
  processing_status = 'pending'
WHERE id = $doc_id;

-- 3. 后台任务会根据新的策略，重新从 extracted_documents 生成组件
```

### 3. 资源复用检查
```sql
-- 检查同一个图片资源在哪些知识库文档中被使用
SELECT d.title as document_title, kb.name as knowledge_base_name, p.photo_description
FROM unifiles.photos p
JOIN unifiles.components c ON p.component_id = c.id
JOIN unifiles.documents d ON c.document_id = d.id
JOIN unifiles.knowledge_bases kb ON d.knowledge_base_id = kb.id
WHERE p.extracted_asset_id = $asset_id;
```

## 🚀 实施优势

### 1. 参考并优化原有实现
-   保留了原有的 `documents`, `components`, `chunks`, `photos` 概念，降低理解成本。
-   通过引入 `files` 和 `extracted_documents` 层，使数据处理的每个阶段职责更清晰、更解耦。

### 2. OCR前置处理
-   OCR/内容提取作为文件处理的独立步骤，生成标准化的Markdown。
-   为后续灵活、高效的分块和索引提供了高质量的、统一的输入源。

### 3. 自定义分块策略
-   用户可以在知识库或单个文档级别自定义分块策略。
-   同一个源文档可以根据不同业务需求（如长文本摘要 vs. 精准QA）生成不同的组件集合，最大化内容价值。

这个设计既保持了原有架构的优势，又通过引入清晰的抽象层次，实现了更高的灵活性、可维护性和扩展性。
